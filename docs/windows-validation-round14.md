# Windows 第14轮：高缩放图块文字与表格几何

日期：2026-10-23。正常规模，针对第13轮留下的局部缺字现象定位并修复。
本轮新增第64个内核补丁并实际增量编译，不是另造办公内核，也没有发布、
生成安装包或替换原安装版。所有输入均为合成测试文件及其副本。

## 根因与修改

当前屏幕168 DPI（175%）。旧版在首图块、1秒和3秒后的窗口画面中仍有缺字；
绕过窗口直接获取内核图像，同样可复现，所以不是单纯截图太早或窗口拼接。

客户端已经按缩放与屏幕DPI计算图块像素数；Windows内核又从屏幕设备继承
168 DPI，而LOK图块的坐标换算按96 DPI计算。重复缩放使内容偏大，跨图块时
被裁去一部分，同时使表格内容与应用表头的行列位置不一致。

`0064-lok-windows-use-logical-screen-dpi.patch` 在Windows图形设备的分辨率入口，
仅对活动LOK的非打印设备使用96 DPI。客户端仍负责实际像素密度，没有改动
系统缩放设置。直接打印设备与非LOK分支保留原来的设备分辨率读法；非打印
虚拟设备也在修改范围内，因此不能据此宣称所有导出与打印都不受影响。

修复后，同一演示的标题和正文完整显示，缩略图比例恢复；表格内容与表头
对齐；文档样本的英文、中文、emoji完整显示。A1因列宽不足且相邻B1有值而
出现的正常截断/红色溢出标记仍保留，不把这种情况误说成数据丢失。

## 保留的失败与纠正

初次Doc/Show并行完整测试触发系统提交内存余量低于2 GiB保护，运行器只停止
各自Job。失败目录`ely-trial-round14-doc-full-20261023-204437-ca140758`、
`ely-trial-round14-show-full-20261023-204437-0fe7cf89`保留，不计为通过，
未调低保护阈值、清理其他程序或修改系统分页文件；随后改用串行复验。

初版Calc合成FODS未写XML声明，被内核识别为通用XML数据表；诊断图可见
`ns1:style-name`等列名。其早期色块/扫描线/绿色实验失败不能作为产品缺陷
基线，也不是本轮又修复一个内核bug。最终修正测试输入识别头，去掉临时诊断
写入，使用不会与红色拼写/溢出标记混淆的绿色填充，严格位置断言通过。
相关旧结果及`calc.fods`、`calc-224.png`保留；最终3项与早期测试二进制哈希不同。
